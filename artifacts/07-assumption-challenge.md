# Devil's Advocate: Plan Review

## Core Understanding

This plan implements a 6-phase, 27-step pipeline to test whether transformer middle layers encode a format-agnostic semantic substrate ("protocol layer") by extracting hidden states from ~800 product descriptions across 5 text registers, analyzing representational geometry via RSA (primary) and linear probes (secondary), with controls for memorization (fictional products), generator confounds (multi-source generation), quantization artifacts (FP16 subset), and anisotropy (PCA-whitening). The plan is structured around 4-5 evening sessions of 3-5 hours each, with tiered scope-cutting to ensure minimum viable results within 8-10 hours.

## Challenged Assumptions

1. **"Qwen3.5-27B exists as a public model."** The plan itself flags this in Open Question #1, but the entire architecture, VRAM budgets, layer count assumptions (64 layers, 3584 hidden dim), and extraction timing estimates are built around this specific model. If the actual available model is Qwen2.5-27B-Instruct-GPTQ-Int4, it may have different layer counts, hidden dimensions, or quantization characteristics. More critically, if only Qwen2.5-Coder variants are available in 27B GPTQ, the model's pretraining distribution (code-heavy) could systematically affect how product descriptions are represented. The plan treats model selection as a trivial lookup at implementation time, but it is actually a design decision that could change VRAM budgets, extraction timing, layer-zone boundaries, and even the hypothesis test results.

2. **"Batch size 1 at ~0.5 sec/stimulus gives ~7 minutes for 800 stimuli on Qwen 4-bit."** This estimate appears in the Risk Assessment (Section 2.1) and is carried into the schedule. But this assumes forward-pass-only time. The plan also requires: (a) forward hooks capturing attention and MLP outputs at every layer, (b) detaching and moving tensors to CPU after each layer, (c) mean pooling, (d) incremental HDF5 writes with gzip compression. Each of these adds overhead. A more realistic estimate for the full extraction pipeline (forward pass + hook capture + CPU transfer + pooling + compressed HDF5 write) is 2-5 seconds per stimulus, giving 25-65 minutes for 800 stimuli. This does not break the schedule, but the plan's timing assumptions cascade -- if Qwen 4-bit takes 60 minutes instead of 7, it pushes Llama extraction into Evening 2 and compresses analysis time.

3. **"GroupKFold with product_id prevents data leakage."** This is correct for preventing same-product leakage, but it creates a new problem: with 80 products (40 real + 40 fictional) and 5 folds, each fold's test set has 16 products. For the 40-class real-product probe, that means each test fold has only 8 real products. The macro-F1 score is computed over the 8 classes present in the test set, which varies across folds. This makes fold-to-fold comparison noisy and the aggregate F1 potentially misleading. More importantly, if the plan trains a 40-class probe but only tests on 8 classes per fold, the probe's learned decision boundaries for the 32 unseen test classes are never validated in that fold. The plan does not address how to compute meaningful aggregate metrics under GroupKFold with 40 classes.

4. **"The debug config (Qwen2.5-1.5B, 2 categories, 2 products/category) is an adequate development proxy."** A 1.5B model has a fundamentally different architecture (fewer layers, smaller hidden dim) than the 27B target. Code that works on 1.5B may silently fail on 27B due to: different module naming conventions in the model class, different attention head configurations, different quantization kernel behavior, or memory patterns that only manifest at scale. The debug config validates code logic but not the integration with the actual model. The plan has a VRAM validation gate (Step 3.1) with a 1-stimulus pilot on the real model, which partially addresses this -- but only for extraction, not for downstream analysis stages that assume specific layer counts.

5. **"Stimulus generation via Claude Sonnet at temperature=0.7 will produce register-distinct texts."** The plan assumes that prompting Claude with register specifications (voice, tone, structure, vocabulary) will produce texts that genuinely vary in surface form while preserving semantic content. But modern LLMs have strong tendencies toward "helpful assistant" style regardless of register instructions. A patent-style prompt may produce text that reads like "a helpful explanation of a patent" rather than actual patent language. Similarly, social media style may produce sanitized, well-structured short text rather than authentic informal register. If register variation in the generated stimuli is shallow (vocabulary swaps rather than genuine structural/pragmatic differences), the entire experiment tests a weaker hypothesis than intended. The plan includes a 5% manual spot-check, but this is a quality assessment, not a quantitative measure of register distinctiveness.

6. **"Permutation tests with 10,000 permutations are computationally feasible at all required stages."** The plan calls for permutation tests for RSA significance (Step 4.3), which means 10,000 permutations x number of layers x number of correction methods x number of model RDMs. For Qwen alone: 10,000 x 64 layers x 2 correction methods (corrected + uncorrected) x 3 model RDMs (product, register, within-category) = 3,840,000 RSA correlations. Each requires computing a Spearman correlation on ~320,000 pairs. This is likely manageable (Spearman on 320K values takes ~10ms, so ~10.7 hours total). But the plan estimates Stage 3 at "1-2 hours" (Architecture, Stage Summary). This is off by roughly an order of magnitude if full permutation testing is done at all layers. The plan needs to decide: permutation tests at peak layer only (fast, as originally planned by the Architect) or at all layers (comprehensive, as recommended by the Domain Expert). This unresolved tension between two specialist recommendations creates a hidden schedule risk.

7. **"The token range 50-200 with length as a covariate is sufficient."** The plan resolved the length debate by allowing 50-200 tokens and using partial RSA to control for length. But partial RSA assumes the length confound is linear (or at least monotonic) in its effect on pairwise distances. If short texts (tweets, 50 tokens) have qualitatively different representation properties than long texts (patents, 200 tokens) -- for example, if short texts are dominated by BOS/EOS effects while long texts have richer internal dynamics -- then linear partial correlation will not fully remove the confound. The plan does not discuss nonlinear confound structures or propose any diagnostic for whether the length correction is adequate.

8. **"The fictional-vs-real comparison uses Spearman r > 0.7 between RSA curves as the pass criterion."** This threshold is arbitrary and untested. What is the expected Spearman correlation between two independent runs of the same analysis on different product subsets of the same type (e.g., two disjoint sets of 40 real products)? Without a baseline for how much RSA curve variation is expected from product selection alone, the 0.7 threshold could be either too lax (passing even when fictional products behave very differently) or too strict (failing due to normal between-subset variation). The plan should either: (a) justify the 0.7 threshold empirically (e.g., split-half reliability of the real-product RSA curve), or (b) acknowledge that this threshold is provisional and define what happens if the correlation is 0.65 or 0.75.

## Gaps Identified

1. **No decision point after stimulus generation quality check.** The plan budgets 30-60 minutes for manual spot-checking 5% of stimuli (Step 2.4), but there is no explicit go/no-go gate or remediation protocol. What if the spot-check reveals that 20% of stimuli have weak register differentiation? What if fictional products' stimuli are systematically shorter or more generic than real products'? The plan should specify: (a) quantitative quality criteria for the stimulus set as a whole (e.g., mean pairwise register distance > X across products), (b) a decision threshold for regeneration, and (c) a maximum number of regeneration cycles before moving on.

2. **No intermediate analysis checkpoint after Qwen 4-bit RSA.** The plan's Evening 2 schedule says "Generate initial phase structure plots -- first look at H1." But there is no explicit decision point about what to do if H1 is clearly falsified at this stage. If middle layers show NO convergence pattern, or if the RSA correlation is flat across layers, should you: (a) proceed with probes anyway (to check if the probe analysis disagrees), (b) investigate the stimuli for quality issues, (c) check the extraction for bugs, or (d) declare early termination? The plan assumes the experiment proceeds linearly regardless of intermediate results. A well-designed plan would include at least one "sanity check" decision gate after the first model's RSA results.

3. **No fallback for the cross-generator control if GPT-4 API is unavailable or too expensive.** The plan specifies 100 additional GPT-4-generated stimuli (10 products x 5 registers x 2 variants). At current GPT-4 pricing, this costs perhaps $3-5 and is unlikely to fail. But the plan does not specify which GPT-4 variant (gpt-4, gpt-4-turbo, gpt-4o), and model availability/pricing changes. If the OpenAI API is down during Evening 1, or if the user's account has expired, there is no fallback. The plan should specify: (a) the exact model ID, and (b) an alternative (e.g., Gemini, or a local model) if GPT-4 is unavailable.

4. **No plan for verifying that mean pooling is appropriate before committing to the full analysis.** The plan records both mean pooling and last-token pooling (Domain Expert recommendation #7) but only discusses last-token as a "robustness check" in the reporting phase. If mean pooling and last-token pooling produce divergent results (e.g., different peak layers, different RSA magnitudes), this is not just a robustness finding -- it calls into question which representation the analysis is actually studying. The plan should include an early diagnostic: after extracting the first model, compute RSA with both pooling methods on a subset and check whether they agree on the basic phase structure. If they diverge, this needs to be addressed before running the full analysis.

5. **No handling of the "what if Qwen and Llama disagree" scenario.** The plan uses Llama-3.1-8B as cross-model validation (Tier 2). But it does not specify what constitutes "agreement" between models, or what to conclude if they disagree. If Qwen shows a clear protocol-layer effect but Llama does not, is this: (a) evidence that the effect is architecture-specific (interesting but weakens the universal "protocol layer" claim), (b) evidence that model size matters (27B vs 8B), or (c) evidence that quantization affects Qwen's results (since Llama runs at a different precision)? These are confounded because Qwen and Llama differ in size, architecture, training data, and quantization simultaneously. The plan should pre-register what the cross-model comparison is expected to show and what divergence means.

6. **No specification of how to handle NaN/Inf in hidden states from specific stimuli.** Step 3.5 mentions "OOM handling: catch CUDA OOM, log stimulus, clear cache, skip and continue." But NaN/Inf values can appear without OOM -- they can result from specific input sequences that trigger numerical instability in quantized layers. The HDF5 validator (Step 1.4) detects NaN/Inf after the fact, but the extraction pipeline should check per-stimulus and either skip or flag problematic stimuli before they contaminate the dataset. A single NaN stimulus in the HDF5 archive will produce NaN in all pairwise distances involving that stimulus, silently corrupting the RDM.

7. **No versioning strategy for intermediate artifacts.** The plan specifies that each stage produces well-defined artifacts (JSON, HDF5, NPY, CSV) and can be re-run independently. But if Stage 2 is re-run after fixing a bug, the old HDF5 files are presumably overwritten. If Stage 3 was already run on the old HDF5, its results are now stale. The plan does not specify: (a) how to detect stale downstream artifacts, (b) whether to use content hashing or timestamps for cache invalidation, or (c) whether to keep old versions of artifacts for comparison. The `config_hash` field in StimulusDataset (Step 2.1) is a step in the right direction, but there is no equivalent for HDF5 or analysis outputs.

8. **Control task probe training time may be underestimated.** Step 5.2 says control probes "double the number of probe fits (~15,360 total)." But this assumes one control probe per real probe. The Hewitt & Manning (2019) methodology recommends multiple control runs (e.g., 10 random label permutations per real probe) to estimate the distribution of control accuracy, not just a single point estimate. With 10 permutations, the total becomes ~76,800 probe fits, taking roughly 10 hours at 0.5 sec each. This exceeds a single evening session. The plan should specify: (a) how many control permutations, and (b) whether this can be parallelized or must run sequentially.

## Risk Scenarios

1. **The actual available Qwen model has different module naming, breaking forward hooks (Likelihood: MEDIUM, Impact: HIGH).** The hook implementation (Step 3.3) assumes `model.model.layers[i].self_attn` and `model.model.layers[i].mlp`. But GPTQ-quantized models from different providers (TheBloke, Qwen official, etc.) may wrap layers differently. For example, some GPTQ models use `model.model.layers[i].attn` instead of `self_attn`, or the quantized linear layers inside `self_attn` may have different names. The 1-stimulus pilot (Step 3.1) catches this, but the plan does not allocate time for debugging hook registration on an unfamiliar model architecture. Budget 30-60 minutes for this.

2. **PCA-whitening with n_components=min(N-1, D) = 799 takes unexpectedly long per layer (Likelihood: MEDIUM, Impact: MEDIUM).** PCA on 800 samples x 3584 dimensions requires computing an 800x800 Gram matrix (fast) or a 3584x3584 covariance matrix (slower). sklearn's PCA should use the efficient path (Gram matrix) since N < D, but this is not guaranteed for all sklearn versions. At 64 layers x 2 models x multiple correction methods, slow PCA could add hours. The plan assumes PCA is fast but does not profile it.

3. **Partial RSA implementation produces incorrect results due to subtle statistical errors (Likelihood: MEDIUM, Impact: HIGH).** Partial correlation on RDM vectors involves regressing out nuisance variables from both the observed and model RDM upper triangles, then correlating residuals. This is conceptually simple but has pitfalls: the nuisance RDMs must be constructed correctly (matching the same stimulus ordering), the regression must handle multicollinearity between nuisance regressors, and the resulting partial correlation has different degrees of freedom than the raw correlation. Errors here would silently produce incorrect p-values for the primary H1/H2 tests. The plan includes unit tests for partial RSA on synthetic data (Step 4.5), but synthetic data may not exercise the edge cases that arise with real RDMs.

4. **FDR correction across all layers eliminates all significant effects (Likelihood: MEDIUM, Impact: MEDIUM).** With 64 layers and multiple model RDMs, FDR correction applies to hundreds of tests. If the true effect is concentrated in 5-10 layers, FDR correction at q=0.05 may still retain significance at peak layers. But if the effect is diffuse (mild elevation across many layers without a sharp peak), FDR correction could eliminate all significant layers. The plan says "Report uncorrected results alongside corrected," which is appropriate, but does not address what to conclude if corrected results are null but uncorrected show a clear pattern. This is the most likely ambiguous outcome.

5. **Evening 1 takes longer than 4 hours, pushing the entire schedule back (Likelihood: HIGH, Impact: MEDIUM).** Evening 1 includes: (a) scaffolding the entire project (pyproject.toml, config system, product catalog, utility modules, test infrastructure -- Steps 1.1-1.5), (b) generating 900+ stimuli via API, (c) quality-checking 5% manually, (d) downloading and loading the primary model (~15GB download + ~14GB VRAM load), (e) running the 1-stimulus pilot, and (f) beginning full extraction. Steps 1.1-1.5 alone involve writing ~10 files with substantial logic (Pydantic config, 80 product definitions, 5 register specs, 40 fictional products with attributes, seed utilities, HDF5 validation, checkpoint system, test fixtures). This is realistically 2-3 hours of coding even for an experienced developer with AI assistance. Adding stimulus generation (30-60 min with API calls + spot-checking) and model loading/piloting brings Evening 1 to 3-4 hours before extraction even starts.

6. **The experiment produces a "qualified GO" that is difficult to interpret or publish (Likelihood: HIGH, Impact: MEDIUM).** The Go/No-Go logic (Step 6.3) defines QUALIFIED_GO as "H1+H2 supported + controls passed, H3 marginal." This is the most likely outcome (per the Risk Assessment's "Results are ambiguous / partially supporting" risk rated HIGH likelihood). But a qualified GO means: middle layers show the predicted phase structure and content dominance, but the protocol-zone advantage over other layers is not convincing. This is a result that supports the three-phase model of transformer processing (already well-documented) but does not establish the stronger "protocol layer" claim. The plan does not discuss how to frame this outcome in a publication, or whether it changes the follow-up experiment plans.

## Key Questions for the User

1. **Have you verified which Qwen 27B GPTQ model is actually available on HuggingFace, and does it have the expected 64 layers and 3584 hidden dim?** If the available model differs from assumptions, the VRAM budget, zone boundaries, timing estimates, and hook module paths all need updating. A 5-minute search now could save hours of debugging later. -- *Priority: high*

2. **What happens if the first RSA results (Evening 2) show a flat correlation curve with no middle-layer peak?** The plan has no explicit decision gate here. Options include: (a) check stimuli quality more carefully, (b) check extraction for bugs by comparing hook outputs to output_hidden_states, (c) try uncorrected representations if the corrected ones are flat, (d) proceed to probes to see if they show anything, (e) stop early. Which of these is your intended response? -- *Priority: high*

3. **How many control task permutations do you intend to run per probe?** A single permutation gives a point estimate of control accuracy that may be unreliable. The standard recommendation is 5-10 permutations to estimate the distribution. But this multiplies probe training time by 5-10x, which could exceed available compute time. -- *Priority: high*

4. **Are you comfortable with the permutation test scope?** The plan has an unresolved tension between the Architect's recommendation (permutation test at peak layer only) and the Domain Expert's recommendation (permutation test at all layers with FDR correction). At all layers with 10,000 permutations, this could take 5-10 hours per model. At peak layer only, it takes minutes but provides less comprehensive evidence. Which do you prefer? -- *Priority: high*

5. **What is your contingency if Qwen and Llama produce contradictory RSA profiles?** The plan uses Llama as cross-model validation but does not pre-register what "validation" means quantitatively, or what to conclude from disagreement. -- *Priority: medium*

6. **Will you compute the split-half reliability of RSA curves to calibrate the r > 0.7 memorization control threshold?** Without knowing the baseline between-subset RSA correlation, the 0.7 threshold is arbitrary. -- *Priority: medium*

7. **Is the token range question (Open Question #7) actually resolved?** The plan says 50-200 is acceptable with length as covariate, but also says prompts target 80-150. If most stimuli end up in 80-150, the partial RSA has limited length variance to work with. If some registers naturally produce 50- or 200-token stimuli, the length confound is substantial but potentially nonlinear. How will you verify that the length correction is adequate? -- *Priority: medium*

8. **Have you considered running a tiny end-to-end pilot (2 products, 2 registers, small model) before committing to Evening 1's full scaffolding?** The debug config exists for this purpose, but the schedule does not explicitly include a full-pipeline dry run. Running the entire pipeline end-to-end on trivial data would validate the inter-stage data contracts before you invest in generating 800+ real stimuli. -- *Priority: medium*

## Alternative Perspectives

### Schedule structure: Pipeline-first vs. Breadth-first

The current schedule builds the pipeline depth-first: complete all scaffolding, then all stimulus generation, then all extraction, etc. An alternative approach builds the pipeline end-to-end first on a minimal subset (2 products, 2 registers, tiny model), validates the entire data flow, then scales up. This would catch integration issues (e.g., HDF5 schema mismatches between extraction and analysis, label indexing bugs in GroupKFold, partial RSA input format errors) early, when they are cheap to fix. The current plan risks discovering in Evening 3 that the analysis code cannot consume the HDF5 format produced in Evening 1-2, requiring rework under time pressure.

### Permutation test efficiency

Rather than running full 10,000-permutation tests at every layer, consider: (a) run a fast 100-permutation screen at all layers to identify candidate significant layers, (b) run full 10,000-permutation tests only at the top-5 candidate layers plus the pre-registered peak layer. This reduces computation by ~95% while retaining the comprehensive layer scan and the rigorous significance testing at key layers.

### Probe alternative: k-nearest neighbor classification

Given the severe sample-size limitation for the 40-class probe (10 samples per class), consider supplementing logistic regression with k-NN classification (k=1 or k=3). k-NN makes no assumptions about linear separability, requires no regularization tuning, and is more natural for the "representational geometry" framing. If 1-NN accuracy is high at middle layers, it directly demonstrates that same-product representations are nearest neighbors -- a stronger geometric claim than "a linear boundary exists." This requires zero additional infrastructure (sklearn KNeighborsClassifier) and provides a complementary perspective on probe results.

## Overall Assessment

The plan is thorough, well-structured, and has clearly benefited from multiple rounds of specialist input. The major design decisions (RSA primary, 40-class probe, GroupKFold, control tasks, partial RSA, anisotropy correction) are all sound. The tiered scope-cutting strategy provides a realistic fallback path.

The **single biggest risk** is schedule compression. Evening 1 is overloaded: it contains the entire project scaffolding (5 steps, ~10 files of non-trivial code), stimulus generation, model download/validation, and the start of extraction. Even with AI-assisted coding, this is 5-6 hours of work, not 4. If Evening 1 slips, every subsequent evening is compressed, and the scope-cutting tiers start activating earlier than planned. The plan would benefit from either: (a) splitting Evening 1 into two sessions (scaffolding + stimuli on one evening, model validation + extraction on the next), or (b) acknowledging that the 5-evening estimate is optimistic and planning for 6-7 sessions.

The **second biggest risk** is the absence of intermediate decision gates. The plan is built as a linear pipeline with a single go/no-go at the end. But the most expensive stages (extraction, probe training) happen before any results are visible. Adding a lightweight "sanity check" after the first RSA results would allow early detection of stimulus quality issues, extraction bugs, or a genuinely null effect -- any of which would change how the remaining time is spent.

The **third biggest risk** is the unresolved computational cost of permutation testing. The plan's time estimates for Stage 3 (1-2 hours) are based on the RSA computation alone, not including the 10,000-permutation significance tests that the Domain Expert recommended at every layer. The full permutation testing regime could take 5-10 hours per model, which would consume an entire evening session by itself. This needs to be explicitly scoped before implementation begins.
